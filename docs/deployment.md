# Render deployment — free web services

The root `render.yaml` Blueprint creates two free Node web services in Frankfurt: `deal-web` (Next.js) and `deal-api` (NestJS). The browser still calls same-origin `/api/v1/*`; the Next server proxies those requests to the API's public Render TLS origin because free services cannot receive private-network traffic. Production deployment never runs the seed.

## Free-tier operational constraints

- Render may spin each service down after 15 minutes without inbound traffic. A request that needs both services can therefore wait for the frontend and then the API to wake.
- A workspace receives a shared monthly free-instance-hour allowance. Two continuously busy services can exhaust it before month end.
- Free services do not support pre-deploy commands. The API start command therefore runs the idempotent `prisma migrate deploy` before starting NestJS. This is a deliberate, non-standard free-tier compromise: migrations add to cold-start time, but a failed migration prevents the API from serving against an incompatible schema.
- Free services cannot receive private-network traffic. `DEAL_API_ORIGIN` is linked to the API's public `RENDER_EXTERNAL_URL`; browser credentials remain same-origin because the browser still talks only to `deal-web`.
- Render does not recommend free instances for production availability. Upgrade both services and restore a separate `preDeployCommand` plus private `hostport` wiring before sustained paid traffic.

## Before the first Blueprint sync

1. Confirm Frankfurt is also appropriate for the Neon database. Change both service regions together if the database is elsewhere.
2. Create a private Cloudflare R2 bucket. Configure CORS for the exact frontend origin and allow `PUT`, `GET` and `HEAD` for presigned file operations. Never enable public bucket access for deal files.
3. Configure LIVE payment accounts and webhook endpoints:
   - `https://<api-host>/api/v1/webhooks/flutterwave`
   - `https://<api-host>/api/v1/webhooks/paystack`
4. In Render Blueprint setup, provide every environment variable marked `sync: false`.

## Required secrets and connections

- `NEON_DATABASE_URL`: pooled runtime URL with `sslmode=require` or `sslmode=verify-full`.
- `NEON_DIRECT_URL`: direct Neon URL used only by `prisma migrate deploy`.
- `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_S3_ENDPOINT`.
- `FLW_SECRET_KEY`: live secret key. Production boot rejects keys containing `TEST`.
- `FLW_WEBHOOK_SECRET_HASH`: at least 16 characters and identical to the Flutterwave dashboard value.
- `PAYSTACK_SECRET_KEY`: an `sk_live_` key. Production boot rejects test or missing keys.

`JWT_ACCESS_SECRET` is generated by Render. `FRONTEND_URL` and the frontend's private API address are wired between services by the Blueprint.

## Deployment behavior

- API build: `npm ci && npm --workspace @deal/backend run build`
- API start: `npm --workspace @deal/backend run db:deploy && npm --workspace @deal/backend run start`
- Web build: `npm ci && npm --workspace @deal/frontend run build`
- Web start: `npm --workspace @deal/frontend run start`
- Node is pinned by `.node-version` and bounded by the root package engines.
- Deploys occur only after repository checks pass.

If a custom frontend domain is added, replace `FRONTEND_URL` with its exact `https://` origin before sending live checkout links. Keep the Render origin as a second comma-separated origin only if users still access it. Update R2 CORS to the same exact browser origins.

## Health checks

- `GET /health` — API liveness.
- `GET /health/live` — explicit liveness.
- `GET /health/ready` — readiness, including database connectivity; Render uses this path.

## Data policy

`backend/prisma/seed.ts` remains available for isolated testing databases. It must not be included in a live deploy command. The seed has its own production guard, but deployment safety does not depend on that guard: `render.yaml` runs migrations only.

## Release verification

Run `npm run verify` before release. Then exercise signup, creator onboarding, project creation, client acceptance, both live payment rails, webhook confirmation, protected review-copy access, final-file release, disputes, and logout against the deployed services. Database-, R2-, and provider-backed suites require real test credentials and are not replaced by the unit suite.
